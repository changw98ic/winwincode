# ADR-0012：角色回合只有产出完整且验证通过的制品才算成功

- 状态：已接受
- 日期：2026-08-22
- 对应任务：`winwincode-9c4.3.3`
- 实现：[`packages/strongflow/src/role-runner.ts`](../../packages/strongflow/src/role-runner.ts)
- 测试：[`tests/strongflow-role-runner.test.mjs`](../../tests/strongflow-role-runner.test.mjs)

## 结论

`StrongFlowRoleRunner` 每次只向一个已经受管的角色会话提交一个新回合。调用方必须提供：

- 与角色声明完全一致、带固定身份的输入制品；
- 与角色所欠输出种类完全一致的制品校验器；
- 上一次中断或恢复前已经消耗的回合、时间、Token 和费用；
- 将内核事件和最终结果写入持久记录并同步到磁盘的记录器；
- 根据固定 DSH 模型路线计算累计费用的计费器。

运行器不会接受模型自己说“完成”。模型最终消息必须是单独一个 JSON 对象：

```json
{
  "schemaVersion": 1,
  "artifacts": [
    { "kind": "REQUIREMENT_SPEC", "artifact": {} }
  ]
}
```

数组的数量、种类和顺序必须逐项等于当前角色规范中的 `requiredOutputArtifacts`。缺少、多出、换序、版本错误、Markdown 代码块、JSON 前后附带说明，以及任何一个制品校验失败，都会得到明确的非成功结果。

因此，Requirements Analyst 必须返回一个 `REQUIREMENT_SPEC`；Solution Architect 必须一次返回 `SOLUTION_DESIGN`、`SYSTEM_ARCHITECTURE_DIAGRAM` 和 `PROCESS_FLOW_DIAGRAM`；Planner 必须返回一个 `EXECUTION_PLAN`。其余五个角色按同一规则返回各自固定的报告或变更清单。

## 为什么校验器由制品模块提供

角色运行器负责“什么时候提交、看哪些事件、怎样计算上限、哪些输出种类齐全”，不在这里提前定义 RequirementSpec、SolutionDesign 等所有字段。后续制品任务 `winwincode-9c4.6.1` 会建立这些对象唯一的版本化数据格式和校验器，再通过本 ADR 固定的接口接入运行器。

这个分工不会保留两套格式：模型输出仍只有一个外层信封；具体制品只有后续制品模块提供的一套格式。校验器还能把程序掌握而模型无法伪造的作业身份、生产者身份、内核事件范围和使用量写入最终制品。

## 事件范围和预算

每个成功或失败结果都保留已经验证的输入制品身份，并包含同一种 `StrongFlowKernelEventInterval`：实际内核会话、事件流、恢复代数、回合标识、首尾内核序号和事件数。没有产生内核事件的提交失败也会明确记录空范围，而不是省略证据来源。

运行器只跟随原生接口返回的准确回合标识。它从匹配的开始事件一直读到匹配的结束事件；另一个回合插入、事件身份变化或序号倒退都会失败。每个原始事件在解释前先交给记录器，最终结果也必须写入并执行 `flush`。

回合数、累计 Token、累计费用和总墙钟时间都从角色规范中的固定预算读取。恢复运行必须带入此前的消耗，不能把重启当作重新获得预算。Token 取自 Codex 的累计 `token_count` 事件；费用由固定模型路线的计费器根据累计 Token 计算。没有累计使用量、计费失败、数值倒退或超过任何上限都不会返回成功。

## 明确失败和清理

以下情况都有稳定的非成功结果：输入或校验器不匹配、提交没有启动新回合、事件流损坏、模型错误、工具失败、沙箱拒绝、取消、超时、预算超限、使用量缺失、输出格式错误、制品验证失败、记录失败和会话清理失败。

取消会记录为 `cancelled` 并打断准确的内核会话。超时、预算超限、模型、工具、沙箱或记录错误会把角色会话记录为 `failed`；如果回合仍在运行，会先打断再关闭。只有制品全部通过验证、会话正常释放、结果记录完成并同步后，调用方才拿到成功结果。

## 八角色隔离验证

[`tests/strongflow-role-isolation.test.mjs`](../../tests/strongflow-role-isolation.test.mjs) 使用独立的内核事件通道和可检查的上下文安装器并行运行八个角色。测试逐个核对模型路线、私有输入、输出种类、可见工具、工作区模式和目录、预算、事件范围、最终释放结果，确认一个角色的私有输入不会出现在另一个角色的提交内容中。另一组脚本化 DSH 模型流让八个角色全部经过真实内嵌 Codex Core 会话完成一次无密钥回合，并再次核对 DSH 收到的模型路线、上下文和私有输入。八个角色还会分别触发 Token 超限，必须各自打断并释放自己的内核会话。Planner 和 Executor 缺少当前 `HUMAN_REVIEW_RECORD` 时不会提交模型回合；Requirements Analyst 把方案字段藏进需求输出时会被制品校验器拒绝。所有角色也会从保存的原上下文分别恢复到新的内核代数，不共享恢复身份。

这里验证的是角色规范、会话边界和运行器怎样执行已安装的权限，不把测试安装器当成操作系统沙箱。真实 Codex 工具可见性、工作区写保护和 macOS/Linux 沙箱后端由 `winwincode-9c4.5.1` 至 `winwincode-9c4.5.3` 建立并再次验证；在这些任务完成前，README 继续明确标注实际工具权限尚未完成。
