# ADR-0003：以原子发布的事件文件保存 StrongFlow 作业

- 状态：已接受
- 日期：2026-08-21
- 对应任务：`winwincode-9c4.2.2`
- 实现：[`packages/strongflow/src/job-store.ts`](../../packages/strongflow/src/job-store.ts)

## 结论

每项 StrongFlow 作业使用一个独立目录和一组不可变事件文件。作业存储不写入 Codex 运行日志，也不写入 DSH 会话记录；三者只通过 `JobId`、`KernelSessionId` 和制品标识关联。

```text
HOME/
└── strongflow-jobs/
    └── SHA256(JobId)/
        ├── manifest.json
        └── events/
            ├── 1.json
            ├── 2.json
            └── N.json
```

目录名使用 `JobId` 的 SHA-256 摘要，避免路径分隔符、长度和大小写规则改变作业身份。`manifest.json` 保存原始 `JobId`、第一个事件标识和创建时间；打开或列举作业时必须重新核对摘要、清单和首事件。

## 首次创建

新作业先在同一 `strongflow-jobs` 目录下写入 `.creating-*` 临时目录：

1. 验证首事件是合法的 `job.created`，且序号为 `1`；
2. 写入并同步清单和首事件；
3. 同步临时事件目录和临时作业目录；
4. 把完整临时目录重命名为最终摘要目录；
5. 同步 `strongflow-jobs` 目录。

最终目录只在全部初始内容已经落盘后出现。同一 `JobId` 的最终目录已存在时，创建以 `JOB_ALREADY_EXISTS` 结束，不覆盖旧作业。进程若在最终重命名前退出，只会留下 `.creating-*`；列举作业会忽略这类从未发布的目录。

## 追加事件

追加事件不直接改写一个长 JSONL 文件。每个事件先写入同一事件目录下的 `.pending-*` 临时文件并同步，再通过硬链接以 `N.json` 原子发布：

```text
.pending-N-UUID.json --link--> N.json
```

硬链接发布具有“不覆盖”语义：两个进程竞争同一序号时，只有一个能创建 `N.json`，另一个得到 `EVENT_ALREADY_EXISTS`。发布后同步事件目录，再删除临时链接。事件文件一旦发布就不再修改。

追加前会读取并重放现有事件，检查：

- `JobId` 与清单一致；
- 新序号恰好接在当前序号后；
- 业务事件能通过纯状态转换函数；
- 事件文件名、事件内序号和事件标识一致。

同一存储对象内的读写还会串行执行；不同对象或不同进程之间则由不可覆盖的最终事件文件解决竞争。

## 唯一的不完整写入规则

恢复规则只有一条：**未发布的 `.pending-*` 和 `.creating-*` 一律忽略；已经使用正式名称发布的内容必须完整有效，否则作业损坏。**

因此：

- 在临时文件写完前退出，不会产生一个正式事件；
- 在硬链接发布后、删除临时链接前退出，正式事件仍有效，多余临时链接被忽略；
- `N.json` 若缺少结尾换行、包含多条记录、JSON 不完整、字段非法或序号不连续，则返回 `STORE_CORRUPT`，不会静默截断或猜测修复；
- 清单缺失、身份变化、未知目录项或首事件不匹配同样视为损坏。

这条规则避免把“最后一行坏了就删除”误用于已经确认落盘的事件。后续启动恢复可以清理陈旧临时项，但清理不会改变投影结果。

## 读取、列举和重放

读取按数值顺序装载 `1.json` 到 `N.json`，逐个执行合同验证，再调用同一个纯投影函数。实时追加返回的快照和重新打开后的快照必须相同。

列举返回每项作业的当前序号、状态、定义版本、当前需求/方案/图身份、批准状态和候选结果标识，不读取或混入 DSH 展示副本。任何已发布作业损坏都会让列举明确失败，避免高级工作台展示一个看似正常但依据不完整的状态。

## 平台边界

第一版只支持 macOS 和 Linux，两者都提供本实现依赖的同文件系统硬链接、原子目录重命名、文件同步和目录同步能力。运行目录必须位于支持硬链接的本地文件系统；能力缺失会返回 `STORE_IO_ERROR`，不会降级成可能被并发覆盖的写法。
