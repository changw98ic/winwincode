# WinWinCode 0.1.0-alpha.1

`0.1.0-alpha.1` 是 WinWinCode 的首个公开预览版。它把 Codex Core 的代码执行能力与 DeepSeek Harness（DSH）的产品界面组合为一个可审核的交付流程。

## 主要能力

- **一个执行内核。** Codex Core 直接嵌入 Rust 原生模块，负责 Thread、Plan、Agent Graph、多 Agent、工具、Shell、MCP、沙箱、权限、Diff 和运行恢复。
- **原始 DSH Chat 默认打开。** DSH 继续负责 Session、模型、Provider、Credential、用户审批交互和 Web/Cordis 外壳。
- **StrongFlow 高级工作台。** WinWinCode 保存 DeliverySpec、验收条件、跨 Session 阶段、业务 Attention、Evidence、逐项结果和 DeliveryVerdict。
- **需求和方案分开审核。** 方案包含系统架构图、流程图、风险和未决事项；绑定的人工 Session 作出当前版本的明确决定后才进入执行。
- **执行过程可检查。** 执行图在执行前显示绿色节点，执行中把受影响节点显示为浅蓝色，候选冻结后把改动节点显示为黄色并开放文件与 Diff hunk 标注。
- **独立验证。** Reviewer 和 Verifier 使用独立 Codex Session，从测试、命令、Diff、文件和运行事件形成直接证据；缺失、过期、冲突或基础设施失败的证据不会产生通过结论。
- **验收结果纠正。** Reviewer 与 Verifier 的结构化结果各有一次格式纠正机会；追加式台账保留全部尝试，Evidence 和 Verdict 只采用最新完整结果。
- **有限返工和恢复。** 人工标注可以绑定当前候选节点与 hunk，进入有限次数的返工；Host 重启后从持久 StageRun、SessionBinding 和运行台账恢复。
- **GitHub 交付闭环。** GitHub Issue 可以成为 Delivery 来源，系统生成确定性的 PR 审核包；远端写入需要当前人工批准，默认执行 dry-run。
- **DSH 模型兼容保持原样。** 真实评估直接选择 DSH 目录中的 Provider 和模型；推理字段与并行工具结果由 DSH 规则生成，不在 WinWinCode 中复制一套 Provider 判断。

## 平台与安装要求

首发包覆盖：

| 操作系统 | CPU | Rust target |
| --- | --- | --- |
| macOS | Apple Silicon | `aarch64-apple-darwin` |
| macOS | Intel | `x86_64-apple-darwin` |
| GNU Linux | arm64 | `aarch64-unknown-linux-gnu` |
| GNU Linux | x64 | `x86_64-unknown-linux-gnu` |

运行时需要 Node.js 24.x。真实模型执行需要在 DSH 设置中选择 Provider、模型和凭据；仓库提供的无密钥 Delivery fixture 可以验证本地流程与边界。

## 数据结构

这是第一个公开候选，因此没有需要迁移的已发布 WinWinCode 数据。该版本创建 `DELIVERY_SCHEMA_VERSION = 3` 数据，并只读取这一当前结构。

未来公开版本改变 Delivery 数据结构时，将随版本提供一次性的离线迁移：从上一受支持版本生成当前版本，在副本上验证后一次替换，并保留原副本用于回滚。

## 当前限制

- 产品以本机单用户 Host 运行；Organization、共享数据库、RBAC、SSO、多租户和跨机器调度不在本版本内。
- StrongFlow 浏览器已支持 Delivery 创建、跟踪、方案审核、三态执行图和返工标注；完整真实仓库阶段编排主要通过 Host API、CLI 和 Delivery fixture 验证。
- 真实执行质量取决于用户选择的模型、Provider、仓库和验收条件。
- GitHub 远端发布需要显式 live 模式和当前人工决定；Jira、Linear、Slack 与 Teams 连接器尚未提供。

## 验证与供应链

发布候选使用同一源码 commit 完成：

1. TypeScript 与 Rust 的格式、类型、Clippy 和测试；
2. CPB 设计边界、固定 Codex/DSH 来源和 Apache-2.0/第三方通知检查；
3. 四个平台的原生构建、包清单、校验和、干净安装、沙箱和 DSH Host 检查；
4. 一个真实模型与真实仓库 Delivery，包括人工方案审核、独立 Reviewer、Verifier、逐项验收和最终人工交付决定；
5. 汇总四平台 artifact 与真实 Delivery 的产品发布报告。

具体证据流程见 [发布流程](../releasing.md) 和 [产品发布门禁](../release-gate.md)。安全问题使用 [私有漏洞报告](../../SECURITY.md)。
